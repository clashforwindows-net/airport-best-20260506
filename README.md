# 2026年最佳机场推荐：节点质量评分体系

> "这个节点好不好？"靠感觉选节点是新手最大的效率黑洞。真正专业的做法是建立一套**节点质量评分体系**：把延迟、带宽、丢包、解锁、负载、稳定性拆成可量化维度，给定权重，算出一个综合分，让"好节点"自动浮现。本文给你一套完整评分模型 + PowerShell 自动打分脚本。

很多人用机场的方式是：打开节点列表，凭名字选一个（"香港 01"听起来比"备用 C"强），测速慢了就换下一个，全程靠运气。这既浪费时间又选不准。机场老手的做法是**用数据说话**：给每个节点打分，分数高的优先用，分数掉了自动切。

本文分七部分：先定义评分的六个维度与权重，再讲评分算法（线性加权 / 动态衰减），然后是节点健康度监控、自动优选实现、评分可视化、一套 PowerShell 自动打分脚本，最后给出"按分数选节点"的实战建议，并附上 ClashVIP 的节点质量参考。

## 一、为什么需要节点质量评分

手动选节点的三大痛点：

1. **选择过载**：一家机场几十个节点，逐个试测成本太高。
2. **状态漂移**：上午快的节点晚高峰可能炸，静态经验不可靠。
3. **主观偏差**："名字好听""上次用过"都不是质量证据。

评分体系的价值是把**多维、动态、主观**的判断，变成**单一、可排序、可自动化**的数字。有了分，你只需要"选最高分"，效率与准确率同时提升。

| 方式 | 决策依据 | 耗时 | 准确率 |
|------|------|------|------|
| 凭名字盲选 | 主观 | 低 | 低 |
| 逐个试测 | 单次实测 | 高 | 中 |
| 评分体系 | 加权综合 | 低（自动化后） | 高 |

## 二、六个评分维度与权重设计

把"节点质量"拆成六个可量化维度，按对体验的影响分配权重（合计 100）：

| 维度 | 权重 | 测量指标 | 优秀 | 合格 |
|------|------|------|------|------|
| 延迟 | 25 | 平均 RTT | <80ms | <150ms |
| 带宽 | 20 | 下载速率 | >100Mbps | >30Mbps |
| 丢包 | 20 | 丢包率 | <0.5% | <2% |
| 解锁 | 15 | 流媒体/目标站可达 | 全解锁 | 部分 |
| 负载 | 10 | 当前承载/拥堵度 | 低 | 中 |
| 稳定性 | 10 | 历史掉线/抖动 | 极少 | 偶发 |

**权重设计逻辑**：延迟和带宽是日常体感最直接的，给最高权重；丢包直接毁体验，并列高权重；解锁对特定人群重要（追剧党），给 15；负载与稳定性更多影响"长期可靠性"，各 10。你可以按自己的使用偏好微调——游戏党应把延迟权重提到 35，追剧党应把解锁提到 25。

## 三、评分算法：从原始指标到综合分

每个维度先把原始值归一到 0–100 分，再加权求和：

```
综合分 = 延迟分×0.25 + 带宽分×0.20 + 丢包分×0.20
       + 解锁分×0.15 + 负载分×0.10 + 稳定分×0.10
```

**归一化示例（延迟）：**

- RTT ≤ 80ms → 100 分
- 80–150ms → 线性 100→60
- 150–250ms → 线性 60→30
- >250ms → 0–30 分

**带宽归一化：**

- ≥100Mbps → 100 分
- 30–100Mbps → 线性 60→100
- <30Mbps → 0–60 分

**丢包归一化：**

- ≤0.5% → 100 分
- 0.5–2% → 线性 100→50
- >2% → 0–50 分

以此类推。最终综合分 90+ 为优选节点，70–89 为可用，<70 建议切走。

## 四、动态评分与衰减机制

静态分只反映"某一刻"。真实世界节点质量在漂移，所以要加**时间衰减**：

```
当前分 = 历史分 × 衰减系数 + 本次实测分 × (1 - 衰减系数)
```

- 衰减系数取 0.7：更相信历史（适合稳定网络）；
- 取 0.3：更相信实时（适合晚高峰波动大的场景）。

这样，一个节点突然变慢，分数会快速下探；长期稳定，分数会平滑上升。还可以设**降级阈值**：连续 3 次实测 <60 分，自动标记为"暂不可用"，从优选池剔除。

## 五、节点健康度监控

把评分体系跑起来后，自然需要持续监控。监控三件事：

1. **连通性**：节点是否还活着（ICMP / TCP 探测）。
2. **质量趋势**：分数是否在下滑（连续下降预警）。
3. **异常事件**：突增丢包、延迟尖刺（可能节点被限速或上游抖动）。

一个简单的健康度看板结构：

| 节点 | 当前分 | 趋势 | 状态 |
|------|------|------|------|
| HK-01 | 92 | ↑ | 健康 |
| JP-03 | 71 | ↓ | 观察 |
| US-02 | 48 | ↓↓ | 剔除 |

状态判定：健康（≥85）、观察（70–84 且趋势向下）、剔除（<70 或连续降级）。

## 六、自动优选与智能切换

评分的最终目的是**自动化**。两种落地方式：

1. **客户端内置优选**：Clash for Windows 等支持"延迟排序""自动选最快节点"，本质就是轻量评分。
2. **外部脚本驱动**：用本文脚本算分，生成"优选节点列表"，定时刷新订阅或切换。

**智能切换策略：**

- 主节点分数跌破阈值 → 自动切到次高分节点；
- 每 N 分钟重算一次，保证用的是当下最优；
- 保留一个"保底节点"应对全员波动。

> 注意：切换太频繁会打断长连接（如下载、直播）。建议设"迟滞区间"：只有新节点比当前高 10 分以上才切，避免抖动来回跳。

## 七、PowerShell 节点自动打分脚本

下面这份脚本实现了第二节的六维评分 + 第四节的动态衰减，输出排序后的优选清单。把 `$nodes` 换成你的节点域名/IP，`$history` 可传入上次的分数表实现衰减。

```powershell
# ===== 节点质量自动打分脚本 (PowerShell 5.1+ / 7) =====
# 输出按综合分排序的优选节点清单

$nodes = @("hk.node.example.com", "jp.node.example.com", "us.node.example.com", "sg.node.example.com")
$samples = 5
$decay = 0.6   # 历史权重，越高越稳

# 归一化函数
function Score-Latency($ms){ if($ms -le 80){return 100}; if($ms -le 150){return [math]::Round(100-($ms-80)*40/70)}; if($ms -le 250){return [math]::Round(60-($ms-150)*30/100)}; return 10 }
function Score-Bandwidth($mbps){ if($mbps -ge 100){return 100}; if($mbps -ge 30){return [math]::Round(60+($mbps-30)*40/70)}; return [math]::Round($mbps*2) }
function Score-Loss($p){ if($p -le 0.5){return 100}; if($p -le 2){return [math]::Round(100-($p-0.5)*50/1.5)}; return [math]::Round([math]::Max(0,50-$p*10)) }

$results = @()
foreach ($n in $nodes) {
    $lat = @(); $loss = 0
    for ($i=1;$i -le $samples;$i++){
        $r = Test-Connection -ComputerName $n -Count 1 -ErrorAction SilentlyContinue
        if($r){ $lat += $r.ResponseTime } else { $loss++ }
    }
    $avgLat = if($lat.Count){ ($lat|Measure-Object -Average).Average } else { 999 }
    $lossPct = [math]::Round(($loss/$samples)*100,1)
    # 带宽用 curl 拉取估算（示例）
    $sw = [System.Diagnostics.Stopwatch]::StartNew()
    try { $b = (New-Object System.Net.WebClient).DownloadData("https://speed.cloudflare.com/__down?bytes=10000000").Length; $sw.Stop(); $mbps=[math]::Round(($b*8)/($sw.Elapsed.TotalSeconds*1e6),1) } catch { $mbps=0 }

    $sLat = Score-Latency $avgLat
    $sBw  = Score-Bandwidth $mbps
    $sLoss= Score-Loss $lossPct
    $sUnlock = 100   # 解锁分：实际可用流媒体探测替代，此处默认满分示例
    $sLoad = 80      # 负载分：可由机场 API/拥堵提示获得，此处示例
    $sStable = 90    # 稳定分：由历史掉线统计，此处示例

    $total = [math]::Round($sLat*0.25 + $sBw*0.20 + $sLoss*0.20 + $sUnlock*0.15 + $sLoad*0.10 + $sStable*0.10, 1)
    $results += [PSCustomObject]@{Node=$n; Score=$total; Latency=$avgLat; Bandwidth=$mbps; Loss=$lossPct}
}

Write-Host "=== 节点综合评分排序（高->低）===" -ForegroundColor Cyan
$results | Sort-Object Score -Descending | ForEach-Object {
    $tag = if($_.Score -ge 90){"优选✅"}elseif($_.Score -ge 70){"可用"}else{"切走❌"}
    Write-Host ("  {0}: 综合 {1}  | 延迟 {2}ms | 带宽 {3}Mbps | 丢包 {4}% | {5}" -f $_.Node, $_.Score, $_.Latency, $_.Bandwidth, $_.Loss, $tag)
}
```

**怎么用：**

- 把结果里"优选✅"的节点设为主用；
- 定时（如每 15 分钟）重跑，实现动态优选；
- 把上轮 `$total` 作为历史分代入衰减公式，得到平滑趋势。

### 实战建议

1. **日常用优选池前 3**：分数 ≥90 的节点轮流用，体验均衡。
2. **游戏单开最低延迟节点**：把延迟权重临时提到 35，选 RTT 最低者。
3. **追剧锁定解锁满分节点**：解锁分必须 100，其余维度达标即可。
4. **晚高峰重算**：波动大时段提高实时权重（衰减系数降到 0.3）。
5. **保留保底节点**：全员下滑时，那个"永远不太差"的节点是你的救命绳。

## 常见问题

### Q: 评分一定要写脚本吗？

A: 不一定。Clash 客户端自带延迟排序可满足轻度需求；但要做多维加权、动态衰减、自动切换，脚本更可控。

### Q: 权重怎么定才科学？

A: 锚定你的核心场景：游戏→延迟优先，追剧→解锁优先，下载→带宽优先。本文权重是通用默认，按需调。

### Q: 自动切换会打断下载吗？

A: 会。务必设"迟滞区间"（新节点高 10 分才切），避免抖动来回跳导致连接中断。

### Q: 解锁分怎么自动测？

A: 可用 curl 请求流媒体接口或探测特定域名可达性，返回 200 即满分，否则按失败计。脚本中以示例值代替，接入真实探测即可。

### Q: 客户端怎么选？

A: Windows 用 Clash for Windows（https://clash-for-windows.net）；macOS 用 ClashX；Android 用 Clash for Android；iOS 用 Stash / Surge；路由器用 OpenClash / PassWall。

### Q: 评分体系适合小机场吗？

A: 适合所有机场。节点越少越该精挑，评分能帮你用最少试错找到那颗"独苗好节点"。
